# 千人以上族谱数据完整性修复设计

## 问题与目标

Issue #6：https://github.com/yunfengsa/pure-genealogy/issues/6。统计、2D/3D、父亲选择、时间轴及生平册的全量查询只发起一次请求，会被 Supabase 的返回行数上限截断。统计随后用数组长度计算总人数，3D 又允许连线指向未加载的父节点。

目标：在当前权限可见范围内，完整读取所有匹配成员，统计和各视图使用完整结果；加载失败必须明确报错；缺失父节点不导致 3D 崩溃或巡游经过不存在的人物。

## 决策

1. 新增通用分页读取器，每页请求 500 条，使用 `count: "exact"` 核对完整性。各查询保留业务排序，并以唯一 `id` 作为最后排序字段。偏移量按实际返回数量递增，兼容服务端上限低于 500。
2. 必须返回完整结果或错误，不返回成功的部分数据。缺失总数、提前空页、重复 ID、总数变化、数据库错误和网络异常均失败。多个 HTTP 请求不构成数据库快照；等量并发修改仍可能不可检测，本次不新增事务 RPC。
3. 统计继续在服务端对完整结果汇总，包括所有分组；不只修正总数。无需改库或调整 Supabase 配置。未来更大规模再评估 SQL 聚合。
4. 父亲姓名批量查询复用同一规则，ID 去重、每批最多 100 个，避免 URL 过长。生平册父亲可能没有生平，不能仅从生平成员中找父亲。
5. 父亲选择和时间轴改为显式 `{ data, error }` 返回值，调用界面显示加载失败。保留当前导入的独立分页和回滚语义。
6. 3D 连线仅连接集合中存在且不同的两个节点；孤立成员仍保留。巡游复用相同连线规则。2D 的可见父节点查询使用 Set，避免完整数据下重复线性查找。
